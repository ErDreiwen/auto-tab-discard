# Reproducible release package

Run the complete gate from a clean repository root and provide the three disposable-browser executables:

```sh
node scripts/release-gate.mjs --chrome-executable PATH --edge-executable PATH --firefox-executable PATH
```

`scripts/package-release.mjs` is the low-level deterministic packager. Its command-line release mode requires `--evidence FILE`; programmatic fixtures must explicitly set `releaseMode: false`. Use `release-gate.mjs`, rather than calling that low-level command directly, for a release decision. A run without a trusted attestation still executes and retains the complete deterministic candidate and browser evidence, and reports `candidateReady: true` when those gates pass, but its final status remains `blocked`.

Release mode verifies that the requested repository is the actual Git top level, the input is exactly its `v3` directory, the worktree is clean, and no merge, rebase, cherry-pick, revert, or bisect is in progress. It rejects nested repository/dependency roots, symbolic links, credentials/key material, nested archives, and editor/merge residue. It also enforces the release name, version, and archive base name in `docs/release-policy.json`.

The packager validates every JSON file and every local resource named by `v3/manifest.json`, checks manifest message references, and requires every shipped locale to contain the complete English message-key set. The checked-in background declaration is an auditable cross-browser source description. Packaging deterministically derives a Chromium manifest containing only the module service worker and a Firefox manifest containing only the existing background-page module loader. Chromium before 121 rejects a Manifest V3 `background.page`, while Firefox does not enable extension service workers, so the browser-specific manifests are a compatibility requirement rather than optional aliases. Icon-production scratch files remain deliberately excluded.

The release input is the `v3` tree plus the repository-root `README.md`, `FORK_NOTES.md`, MPL-2.0 `LICENSE`, migration and permission notes, release policy, and this packaging guide. Strict release mode requires `FORK_NOTES.md`, `docs/MIGRATIONS.md`, and `docs/PERMISSION_CHANGES.md` to exist and remain non-empty after UTF-8/LF normalization. The root README replaces the source tree's legacy `../README.md` placeholder. UTF-8 text is normalized to LF before hashing and archiving, so equivalent LF and CRLF checkouts produce identical bytes. Paths are sorted, ZIP timestamps are fixed to the 1980 epoch, and file modes are normalized to `0644`.

Artifacts and their `SHA256SUMS`/`checksums.json` metadata are written to ignored `build/results/`. Metadata format 4 contains separate `chromium` and `firefox` records, each with the exact archive name, byte count, SHA-256, normalized tree SHA-256, entry count, and complete path/size/SHA-256 inventory. Shared metadata binds Git commit and tree IDs, release-note digests, locale count, injected root-file list, and repository-relative test-evidence references with byte counts and SHA-256 digests. The target inventories must have identical paths and bytes everywhere except `manifest.json`. These provenance hashes are reproducibility evidence, not a store signature.

The browser-canary workflow is configured to build both target artifacts independently on fresh Linux and Windows hosted runners. Each builder first applies the same clean-worktree, canonical-root, transition-state, symlink, and forbidden-input checks used by strict release context validation, then publishes a `builder-provenance.json` record with its runner identity, commit, Git tree, both archive hashes and sizes, both normalized tree and complete-inventory hashes, metadata hash, and version. `artifact-reproducibility-gate` hashes each downloaded ZIP/XPI itself and fails on any builder, commit, tree, target archive, metadata, inventory, or version mismatch. Linux supplies the canonical Chromium ZIP to the Chrome/Edge jobs and the canonical Firefox XPI to the Firefox job; `browser-canary-gate` rechecks every browser record against its target-specific archive, tree, inventory, and version. Only a successful hosted workflow run is two-machine evidence; local tests and this configured workflow are not represented as a run that already happened.

The gate parses both generated inventories, rejects unsafe/duplicate/nested-manifest paths, extracts only stored entries into target- and digest-named directories, and compares every extracted path, byte count, file hash, and whole-tree hash with its archive. Chrome popup, external-API, form-protection, window-scope, Edge popup, native-frozen, direct-native, and both Chromium upgrade reports must identify the extracted Chromium ZIP tree; the Firefox BiDi report must identify the extracted Firefox XPI tree. A passing browser process is insufficient when its report omits or disagrees with the appropriate artifact-tree hash. The Edge direct-native report must contain exactly the five named popup release scopes, four cancellation phases, and three MV3 worker-termination boundaries; it must also record an exited exact child process, zero crash artifacts, a stopped fixture, and removed disposable profile. The Chrome form-protection and window-scope reports must likewise record zero crashes, an exited isolated browser process, a removed disposable profile, and a stopped fixture server. A second strict package must remain byte-for-byte and inventory-identical to both browser-tested preliminary artifacts before a gate can pass.

`docs/PERMISSION_CHANGES.md` and `tests/manifest-policy.test.mjs` compare the current permission surface with the checked-in 0.6.9.1 baseline. `docs/MIGRATIONS.md` identifies the executable legacy preference and ownership fixtures. The strict gate also requires extracted-artifact upgrade, service-worker restart, browser restart, and rollback reports from both Chrome and Edge. Each report proves zero sleeper requests during extension/worker restart and no more than one browser-originated session-restore request per sleeper, followed by stable request counts through a dwell and rollback. A source-only or fixture-only run is not a passing upgrade claim.

## Signed release-note attestation

The protected `refs/tags/v0.6.9.2` job runs only in `ErDreiwen/auto-tab-discard`, only when GitHub reports that ref as protected, and only after the independent Linux/Windows reproducibility gate and target-aware browser-channel gate both pass. Its privileged job has only `contents: read`, `id-token: write`, `attestations: write`, and `artifact-metadata: write`. Every third-party action in the complete producer, evidence-gate, and signing workflow is pinned to a reviewed full commit SHA, including the browser installers; the final job therefore does not sign outputs that passed through movable action tags. It re-names, without rebuilding, the canonical target-specific ZIP/XPI pair, creates the versioned custom in-toto predicate `https://github.com/ErDreiwen/auto-tab-discard/attestations/release/v2`, signs both exact subjects in one attestation, and retains the bundle and predicate inputs for 90 days.

The predicate binds each target to its exact ZIP/XPI name, SHA-256, archive byte count, normalized archive tree and inventory, and target manifest digest. It also binds the extension version, normalized in-archive SHA-256 and byte count for `FORK_NOTES.md`, `docs/MIGRATIONS.md`, and `docs/PERMISSION_CHANGES.md`, normalized in-archive release-policy digest, Git commit, Git tree, protected tag ref, and the exact byte digests of the passing cross-builder and browser-gate reports. It rejects any non-manifest difference between the target archives. `scripts/release-attestation.mjs verify` recomputes those values rather than trusting predicate claims alone. It invokes the fixed `gh` executable with fixed repository, signer-workflow, signer/source commit digest, source ref, predicate type, SHA-256, GitHub Actions OIDC issuer, and `--deny-self-hosted-runners`; neither production CLI accepts an alternate verifier executable. It requires an on-disk bundle, a separately supplied `trusted_root.jsonl`, and exactly one verified result with the exact predicate and two-subject set.

`docs/github-attestation-trusted-root.jsonl` is the reviewed snapshot produced by GitHub CLI's TUF-backed `gh attestation trusted-root` command on 2026-08-13. The release policy pins SHA-256 `65ca537f6ed8a47fd0e560c421baa1f6c1efb8b25fc200d8c5c02c0e92eb2b9c` over its UTF-8, BOM-stripped, LF-normalized bytes. Verification rejects every other custom root, even when it is well-formed JSONL; path separation from the bundle is necessary but is not treated as authentication. A future TUF rotation must be reviewed and must update the snapshot, policy pin, and code pin together.

After downloading the retained attestation artifact, rerun the local release gate with all four hosted inputs and the reviewed root snapshot:

```sh
node scripts/release-gate.mjs --chrome-executable PATH --edge-executable PATH --firefox-executable PATH --attestation-bundle PATH/release-attestation.bundle.json --trusted-root docs/github-attestation-trusted-root.jsonl --hosted-browser-gate PATH/browsers/browser-canary-gate.json --hosted-reproducibility-gate PATH/reproducibility/cross-builder-gate.json
```

The verifier never downloads a root implicitly when deciding a release. Fake-`gh` substitution exists only as an in-process test dependency and is unreachable through either production CLI. The configured signing job and offline fake-`gh` tests are present, but an actual protected-tag hosted signing run and its resulting bundle are still pending; no current local artifact is represented as signed.

The `.zip` is the service-worker-only Chrome/Edge upload or unpack-and-test artifact. The `.xpi` contains the Firefox background-page loader and is unsigned AMO submission input only; normal Firefox distribution still requires Mozilla signing. Every non-manifest entry is required to be byte-identical across the pair. Source-tree verification has exercised Chrome 151, Firefox 153, Edge 151.0.4129.72's 19-scenario popup matrix, and the Edge direct-native 5/4/3 release, cancellation, and worker-loss matrix. No historical or source-tree result is silently reused: a release is not complete until every gate, including the redesigned native-frozen smoke, passes against the correct final extracted artifact and records that target's canonical digest.

## Fork identity and signing

The manifest uses the fork-owned name, GitHub homepage, and Gecko ID (`{b3b398c4-27bc-46b6-9447-f07deec6aeba}`). README store/review URLs are explicitly labelled upstream references and are not represented as fork listings. The packager does not sign Firefox artifacts: its XPI is AMO upload input, and only the resulting Mozilla-signed XPI is a normal Firefox distribution artifact.
